# MYAGENTS 项目问题复盘与面试参考

> 用途：面试时说明项目背景、问题判断、技术取舍和验证方式。
> 这份记录只包含本项目实际遇到并处理过的问题，不把假设写成结果。

## 一、项目概况

MYAGENTS 是一个本地优先的 Markdown 知识库问答工具。主要链路是：

```text
Markdown 文档
  -> 清洗与父子分块
  -> 本地向量索引 + BM25
  -> 混合召回与可选精排
  -> 规划器与工具执行
  -> LLM 生成回答并返回引用
```

Web 端还负责会话、工作区、反馈、日志、配置和运行指标。macOS 端通过 `.app` 启动本地后端，再打开浏览器页面。

## 二、主要问题与解决方式

### 1. 首次使用必须编辑 `.env`，配置门槛高

**现象**：用户打开页面后不知道 API Key 应该在哪里填写；直接提问时只看到后端报错。

**根因**：配置入口只存在于项目文件，前端没有首轮引导，也没有结构化错误码。

**解决**：

- 增加设置面板，在页面内保存 API 配置；
- 首次检测不到 API Key 时自动打开模型设置；
- `/api/ask`、流式问答和图片问答统一返回 `MODEL_NOT_CONFIGURED`；
- 前端把错误码转换为中文提示，并保留已保存的密钥不回显明文；
- 模型和检索参数提供默认值，复杂参数放进高级设置。

**面试表达**：

> 我把“配置失败”从开发者问题改成了产品流程。后端提供稳定错误码，前端负责引导和恢复，用户不需要打开文件才能完成首次配置。

### 2. 直接打开 HTML 出现 `Failed to fetch`

**现象**：页面看起来能打开，但保存设置或加载数据时报 `Failed to fetch`。

**根因**：用户打开的是 `file:///.../webui.html`。这个页面没有经过 Python HTTP 服务，`/api/config` 等相对路径自然无法访问。

**解决**：

- 页面只通过本地 HTTP 服务提供；
- 对 `file:` 协议做显式检测；
- 把浏览器原始英文错误替换为“请双击 MYAGENTS.app 启动”；
- README 增加正确启动路径和常见问题说明。

**可复用经验**：前端资源地址、API 地址和启动方式必须在产品层面统一，不能假设用户理解 `file://` 与 `http://` 的区别。

### 3. 流式输出时出现 JSON 解析错误

**现象**：页面显示类似 `JSON Parse error`，有时还会把 `HTTP` 当成 JSON 内容解析。

**根因**：NDJSON 流已经发送响应头后，后端异常处理又尝试写第二个 HTTP 错误响应，导致同一连接混入两种协议内容。

**解决**：

- 流式接口在响应头发送后，只继续写合法的 NDJSON 事件；
- 前端逐行解析 `meta`、`delta`、`done`；
- 非 2xx 响应先读取结构化 JSON，再显示中文错误；
- 失败时移除空的 assistant 占位消息，避免留下空卡片。

**面试表达**：

> 我先区分了“HTTP 错误响应”和“已建立的流式协议”两个阶段。流建立后不再切换协议，而是用流内事件表达错误。

### 4. 精排模型下载阻塞启动，界面误报后端断开

**现象**：启动或保存设置后，索引区域显示“后端未连接”；日志显示 Hugging Face 模型下载不断重试。

**根因**：Cross-Encoder 缺失时，代码从离线加载失败回退到联网下载。网络不可用时会进行多轮退避重试，后端在这段时间内无法及时响应。

**解决**：

- 启动阶段只尝试本地目录或已有缓存；
- 模型不存在时立即跳过精排；
- 基础向量检索和 BM25 继续工作；
- 增加回归测试，确保缺失模型只发生一次离线加载尝试。

**技术取舍**：牺牲可选精排能力，换取核心问答可用性和启动确定性。精排属于增强项，不应阻塞主链路。

### 5. 后端已能问答，但索引状态显示“后端未连接”

**现象**：回答功能正常，顶部索引状态仍是红色断开。

**根因**：前端把 `/api/status`、`/api/kb`、`/api/stats` 放在同一个 `Promise.all` 中；任意一个辅助接口失败，都会进入统一 catch，把核心后端标成断开。

**解决**：

- `/api/status` 作为核心连接判断；
- 知识库和统计接口改用 `Promise.allSettled`，各自更新自己的区域；
- 状态轮询使用 `cache: no-store`；
- 页面显示“已连接、重建中、已同步”等真实状态，而不是静态占位文案。

**面试表达**：

> 我把系统状态拆成核心健康度和辅助数据可用性，避免局部失败污染全局状态。这是比简单加重试更重要的状态建模问题。

### 6. 多个端口和旧进程造成启动混乱

**现象**：`8787` 被其他项目占用，旧版 MYAGENTS 又运行在 `8788` 或 `8789`，双击应用后页面可能连到旧服务。

**根因**：启动器只按端口判断，没有可靠区分项目归属和版本。

**解决**：

- 在 `8787–8797` 中选择端口；
- 通过 `/api/status` 的版本字段识别 MYAGENTS；
- 对状态接口失效的进程，读取监听进程工作目录，只清理属于本项目的进程；
- 其他项目即使使用相邻端口也不处理。

**风险控制**：进程清理必须先确认工作目录，不能按端口直接 kill，否则会影响其他本地项目。

### 7. 关闭网页后后端仍然运行

**现象**：用户关闭页面后，Python 后端进程和端口仍占用；下一次启动可能重复拉起服务。

**根因**：普通浏览器关闭页面不会可靠通知本地 Python 服务，不能只依赖 `beforeunload`。

**解决**：

- 前端每 3 秒发送一次本地心跳；
- 后端记录最近心跳；
- 所有页面关闭后超过约 15 秒，后端自动退出；
- 双击 `.app` 时仍会先清理项目遗留实例，作为第二道保险。

**取舍**：保留短暂的退出延迟，避免刷新页面或短时网络抖动误杀后端。

### 8. 会话历史需要跨重启保存，并且记忆不能串线

**现象**：重启服务后会话消失，或不同会话之间共享错误上下文。

**根因**：早期状态主要在进程内存中，缺少持久化存储和会话归属校验。

**解决**：

- 使用 SQLite 保存工作区、会话、消息、反馈和检索事件；
- 每次请求根据 `session_id` 恢复对应的 `SessionMemory`；
- 校验会话是否属于当前工作区；
- 启动后从数据库重新加载会话列表和消息。

**验证**：测试关闭并重新打开 `WebStore` 后，检查消息、记忆和反馈仍存在，并验证不同会话相互隔离。

### 9. 会话删除只删前端或只删消息不完整

**现象**：用户希望删除某条最近会话；如果只清空消息，标题和统计仍然残留。

**根因**：删除操作没有完整覆盖会话、消息和检索统计三类数据。

**解决**：

- 每条会话增加悬停显示的删除按钮；
- 点击后进行二次确认；
- 后端校验会话属于当前工作区；
- 删除会话时级联删除消息，同时清理 `query_events`；
- 删除当前会话后自动切换到下一条或创建新会话。

### 10. 设置项太多，普通用户难以理解

**现象**：模型和检索设置需要填写一堆参数，首次使用成本高。

**根因**：把内部调优参数全部暴露在主界面，没有区分常用配置和高级配置。

**解决**：

- 模型页默认只展示模型服务和 API Key；
- DeepSeek 使用地址、模型、温度和 Token 默认值；
- 检索页提供均衡、快速、深度预设；
- Top K、精排模型和多查询等参数移入可折叠高级区域。

**产品判断**：默认设置解决“能否开始使用”，高级设置解决“能否调优”，两者不应混在同一个首屏。

## 三、工程判断与取舍

### 为什么选择本地优先

- API Key、知识库、会话和日志默认留在本机；
- 服务只监听 `127.0.0.1`；
- 不需要先部署云端服务即可验证产品闭环。

代价是用户需要准备 Python 环境和模型依赖，因此补充了 macOS `.app` 启动器和页面内配置。

### 为什么不让精排模型阻塞主链路

精排只改善召回排序，不是回答链路的唯一信息来源。没有精排时仍可使用向量和 BM25 召回，因此选择可用性优先，并明确记录降级状态。

### 为什么没有用“一个总状态”

后端连接、索引构建、统计查询和模型配置是不同状态。把它们合并成一个布尔值会制造误报，也会让用户无法判断下一步该做什么。

## 四、面试回答模板

### 1 分钟项目介绍

> 我做的是一个本地优先的 Markdown 知识库问答工具。它把文档清洗后建立向量和 BM25 混合索引，通过规划器、工具和模型生成带引用的回答。项目的难点不只是把模型接起来，而是把它做成可使用的产品：我补了页面内 API 配置、跨重启会话、工作区隔离、流式状态、日志和桌面启动。实际排查过 `file://` 导致的请求失败、流式协议混写、精排模型下载阻塞、端口冲突和状态误报，并用结构化错误码、离线回退、心跳和 SQLite 持久化处理。

### 被问“你解决过最难的问题是什么？”

推荐回答“流式输出协议混乱”或“精排模型下载阻塞”。回答结构：

1. 先描述用户看到的现象；
2. 说明如何建立最小复现；
3. 区分根因和次要噪音；
4. 说明技术方案和取舍；
5. 给出测试或日志证据；
6. 说明如果规模扩大，下一步会如何改进。

### 被问“你如何判断功能是否真的解决了问题？”

不要只说“页面能用了”。可以回答：

- 对 `file://` 场景检查是否出现明确中文引导；
- 对未配置模型检查是否返回固定错误码；
- 对流式接口检查 NDJSON 是否始终可逐行解析；
- 对缺失精排模型检查启动是否不发生联网回退；
- 对会话存储检查重启后消息、记忆、反馈和统计是否符合预期；
- 对删除会话检查消息和检索事件是否一起消失。

## 五、当前仍存在的边界

- `.app` 依赖项目目录中的 `.venv`，不能独立复制到任意电脑运行；
- 当前服务适合单机使用，不包含登录、权限和多用户协作；
- 精排模型缺失时会降级，精排质量没有在所有知识库上做系统评测；
- 本地心跳只能近似判断页面是否关闭，存在约 15 秒退出延迟；
- 统计是本地查询事件统计，不等同于完整线上检索质量指标。

## 六、后续改进优先级

| 优先级 | 改进项 | 原因 | 验证方式 |
| --- | --- | --- | --- |
| P0 | 增加启动器和 API 的集成测试 | 当前端口清理与页面心跳依赖真实进程 | 临时端口启动、关闭页面、检查进程退出 |
| P1 | 增加检索评测集和基线 | 当前命中率只能反映事件结果，不能证明检索质量 | Recall@K、MRR、人工相关性标注 |
| P1 | 增加配置迁移和版本兼容 | 运行时配置字段会随版本变化 | 旧配置 fixture 回归测试 |
| P2 | 提供独立打包环境 | 当前 `.app` 依赖项目目录和 `.venv` | 在干净 macOS 环境安装验证 |

## 七、可引用的工程原则

- 先建立可复现的最小问题，再讨论修复方案；
- 区分核心链路和增强能力，增强能力失败时应降级而不是阻塞；
- 状态要按领域拆分，不能用一个布尔值覆盖多个依赖；
- 错误信息要告诉用户发生了什么、已保留什么、下一步做什么；
- 本地进程清理必须先确认归属，避免按端口误杀其他项目；
- 每个用户可见修复都应有对应的回归检查。
