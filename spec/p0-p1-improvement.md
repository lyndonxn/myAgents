# P0/P1 改进规格

版本：v1.0  
范围：myAgents 本地优先 Markdown 知识库问答 Agent  
目标：先解决安全、数据治理、可验证性和任务可靠性，再降低核心模块耦合并提升评测可信度。

## 1. 优先级与交付顺序

| 优先级 | 主题 | 目标 | 交付顺序 |
|---|---|---|---|
| P0 | 测试入口标准化 | 让测试可被自动发现、统一执行、可进入 CI | 1 |
| P0 | 记忆治理 | 用户可查看、删除、清空长期记忆 | 2 |
| P0 | 联网与记忆默认行为 | 降低未明确授权的数据外发与持久化 | 3 |
| P0 | 配置校验 | 在启动或保存时阻止无效配置 | 4 |
| P0 | 密钥与任务写回安全 | 降低密钥泄露和重复写回风险 | 5 |
| P1 | 核心模块解耦 | 降低 Agent/Web/TaskRunner 的修改和回归成本 | 6 |
| P1 | 任务可靠性 | 增加超时、心跳、watchdog 和更细锁粒度 | 7 |
| P1 | 评测扩展 | 验证无答案、多跳、冲突、注入等真实场景 | 8 |
| P1 | 证据级引用校验 | 从编号合法升级到回答与证据的支撑关系 | 9 |
| P1 | 生产配置与错误契约 | 形成稳定的配置、错误码和 API 行为 | 10 |

## 2. P0 规格

### P0-1 测试入口标准化

#### 问题

当前测试主要是可执行脚本，单独运行可以通过，但标准测试发现机制报告 `0 tests`，无法可靠接入 CI、IDE 和覆盖率工具。

#### 目标

- 所有测试可由一个标准命令发现并执行；
- 保持离线，不调用真实 LLM 或网络；
- 保留现有 fake LLM、临时目录和桩对象。

#### 范围

- 采用项目已有依赖中可用的测试框架；若未提供 pytest，则使用标准 `unittest`；
- 将现有脚本式断言封装为可发现的测试用例；
- 保留脚本直接执行兼容性；
- 新增统一入口和失败摘要。

#### 验收标准

- `python -m unittest discover -s tests -p 'test_*.py'` 能发现并执行测试，数量大于 0；
- 统一测试命令一次执行全部离线测试；
- 任一测试失败时返回非 0；
- 测试不访问真实 LLM API、互联网或用户数据目录；
- 至少覆盖工具、Agent、记忆、任务、WebStore、benchmark sample 六类。

#### 指标

- 测试发现数：100%；
- 离线测试通过率：100%；
- 核心模块语句覆盖率目标：≥80%。

### P0-2 长期记忆治理

#### 问题

长期记忆和实体记忆会跨会话保存，但用户目前无法查看、删除或清空；清空会话也不会同步处理长期记忆。

#### 目标

用户能够明确知道哪些内容被记住，并能够撤回、删除或全部清除。

#### 范围

新增后端能力：

- `GET /api/memory?session_id=&q=&limit=`：查看记忆条目；
- `DELETE /api/memory/{episode_id}`：删除单条长期记忆；
- `DELETE /api/memory?session_id=`：删除指定会话产生的记忆；
- `POST /api/memory/clear`：清空长期记忆和实体记忆；
- `GET /api/memory/entities`：查看实体事实；
- 记录 episode 的来源会话、创建时间、最近命中次数。

新增行为：

- “清空会话”提供是否同时删除该会话长期记忆的显式选项；
- 支持本次问答 `remember=false`，不写入长期记忆和实体记忆；
- 删除操作必须同步更新 `episodes.json`、`vectors.npy`、`entities.json`；
- 删除和清空使用临时文件 + 原子替换。

#### 验收标准

- 查询接口不返回完整答案之外的敏感运行字段；
- 删除单条记忆后，重启进程仍不可检索到；
- 按会话删除只影响目标会话；
- 清空后长期记忆和实体记忆均为空；
- `remember=false` 时不产生 episode、vector 或 entity 文件变更；
- 非法 episode ID、越权 session ID 返回明确 4xx，不泄漏堆栈；
- 现有 `SessionMemory` 和 `/api/ask` 默认行为保持兼容。

#### 指标

- 记忆删除成功率：100%；
- 删除后残留召回率：0%；
- 记忆相关请求 4xx/5xx 可观测。

### P0-3 联网与记忆默认行为

#### 问题

长期记忆、实体抽取和 Web 降级默认开启，用户可能在未充分理解的情况下持久化或外发数据。

#### 决策

- `memory.long_term_enabled` 默认改为 `false`；
- `memory.entities_enabled` 默认改为 `false`；
- `tools.kb_fallback_web` 默认改为 `false`；
- 用户在 UI 明确开启后才启用；
- 配置页显示“会保存到本机”与“会发送到互联网”的说明。

#### 兼容策略

- 已有用户的 `runtime.json` 显式配置优先，不强制覆盖；
- 首次升级显示迁移提示；
- `/api/ask` 增加可选 `allow_web`、`remember` 字段，缺省使用配置值；
- 关闭 Web 时，知识库失败必须返回可解释的未命中结果，不自动外发。

#### 验收标准

- 默认新配置不会调用 Web 搜索，不写长期记忆；
- 用户显式开启后，降级和记忆行为恢复；
- UI 在发送前能看到当前联网/记忆状态；
- 日志记录是否发生 Web 降级，但不记录完整敏感问题。

### P0-4 配置校验

#### 目标

在加载配置和保存运行时配置时发现错误，而不是在问答中途才失败。

#### 规则

- 整数范围：`top_k` 1–100、`max_steps` 1–50、`max_retries` 0–5；
- 浮点范围：温度 0–2、超时 >0、权重 0–1；
- 枚举：rerank、fusion、embedding backend 等只接受文档定义值；
- 布尔值只接受 `true/false`、`1/0`、`yes/no`；
- 路径、URL、模型名进行基本格式校验；
- 错误信息必须包含完整配置路径和修复建议。

#### 验收标准

- 无效 YAML 或 runtime 配置不会导致进程静默启动；
- `/api/config` 保存无效值返回 400；
- 有效配置保存后重启仍生效；
- 配置校验不打印 API Key。

### P0-5 密钥与任务写回安全

#### 密钥要求

- 启动时检查 `.env`、`runtime.json` 权限；不满足最小权限时告警并拒绝保存新密钥；
- API 响应永不返回明文 Key；
- 日志、任务记录、消息 metrics 不得包含 Key；
- 提供使用系统钥匙串的后续扩展点，但本期不强制引入新依赖。

#### 任务写回要求

- `TaskRecord` 新增 `writeback_id` 或等价幂等标识；
- 完成回调写回前检查该标识是否已处理；
- 重启、重复回调、网络重试不得产生重复 user/assistant 消息；
- 写回失败必须保留 completed 任务和可重试状态，不回滚任务答案。

#### 验收标准

- 同一任务重复触发完成回调，消息只出现一次；
- 写回异常不会使任务重新执行；
- 密钥在 API、日志、任务 JSON 中均不可见。

## 3. P1 规格

### P1-1 核心模块解耦

#### 目标

降低 `agent.py`、`web_server.py`、`task_runner.py` 的职责重叠和隐式依赖。

#### 目标结构

```text
AgentFacade
├── IndexService
├── RetrievalService
├── PlanningService
├── ExecutionService
├── MemoryService
└── AnswerService
```

#### 约束

- 本期不引入大型框架；
- `Agent.ask()`、`/api/ask`、任务 API 保持兼容；
- 新服务通过明确的数据类传递输入输出，不直接依赖 HTTP Handler；
- 任务路径与普通问答共享 Planning/Execution/Answer 服务。

#### 验收标准

- Web Handler 不直接实现规划、检索或合成逻辑；
- TaskRunner 不依赖具体 Web 类变量；
- 每个服务可用 fake 依赖独立测试；
- 现有测试全部通过，公开 API 无破坏性变化。

### P1-2 任务可靠性与并发

#### 功能要求

- 每个任务记录 `heartbeat_at`、`current_step`、`last_error_type`；
- 支持任务级总超时和步骤级超时；
- watchdog 将超过阈值无心跳的 running 任务转为 paused 或 failed；
- 锁拆分为会话记忆锁、执行锁、写回锁；
- 允许配置有限 worker 数量，默认仍为 1；
- 取消操作在步骤边界生效，必须在 API 中明确说明。

#### 验收标准

- 超时任务不会永久停留在 running；
- worker 异常退出后任务可恢复；
- 两个不同会话可并行执行且记忆不串线；
- 同一会话的问答与任务不会并发修改记忆；
- 取消任务不会被 resume 复活；
- 任务状态迁移非法时返回明确错误。

#### 指标

- running 超时未收敛任务数：0；
- 任务恢复成功率：≥99%；
- 跨会话记忆串线：0；
- 任务重复执行率：0%。

### P1-3 分层评测集

#### 目标

从“能命中来源”扩展到“答案正确、拒答正确、工具选择正确、失败可恢复”。

#### 题型

- 直接事实；
- 多跳问题；
- 无答案问题；
- 冲突来源；
- 工具调用；
- 长上下文；
- 提示注入；
- 跨会话记忆；
- 网络不可用与模型不可用。

#### 指标

- `retrieval_file_hit`；
- `retrieval_section_hit`；
- `task_completed`；
- `answer_correctness`；
- `groundedness`；
- `refusal_accuracy`；
- `tool_selection_accuracy`；
- `p50/p95 latency`；
- 单题 prompt/completion tokens 和成本；
- 失败类型分布。

#### 验收标准

- 公开样例集与私人知识库题目分离；
- 每种题型至少 10 题；
- `--retrieval-only` 不调用 LLM；
- 评测报告同时输出均值、分位数和失败样例；
- 评测结论明确区分事实、推断和样本限制。

### P1-4 证据级引用校验

#### 目标

判断回答是否被来源支撑，而不仅是判断引用编号是否越界。

#### 方案

- 每个来源生成稳定 `source_id`；
- 合成提示要求输出回答段落与 source_id 的映射；
- 校验分三层：编号合法、来源存在、语义支撑；
- 无来源工具（例如主题概览）不强制生成引用；
- 低置信度时输出“证据不足”并保留可核对来源；
- 支撑度评估默认使用规则/检索相似度，LLM judge 仅在显式开启时使用。

#### 验收标准

- 越界引用仍会被清理并计数；
- 合法但不相关的引用会被标记为 unsupported；
- 每条回答可追溯到来源片段；
- 无来源回答不会因为强制引用模板而产生幻觉编号；
- 现有 `citations_valid/invalid` 字段保持兼容，新增字段使用默认值。

### P1-5 API、错误码和生产配置契约

#### 要求

- 为 `/api/ask`、`/api/tasks`、`/api/memory`、`/api/config` 定义请求和响应 schema；
- 统一错误结构：`{code, message, retryable, details}`；
- 区分 400、401/403、404、409、413、429、500、503；
- 为可重试错误标记 `retryable=true`；
- 对 LLM、Web 搜索、知识库、配置和任务状态分别定义错误码；
- 记录 API 版本，例如 `/api/v1/...`，旧路径继续兼容。

#### 验收标准

- 所有新增 API 均有正常、边界、权限、重复提交和依赖失败测试；
- 客户端无需解析自然语言错误来判断是否重试；
- 500 响应不包含堆栈、路径或密钥；
- README 或独立 API 文档与实现一致。

## 4. 非目标

本期不做：

- 多租户权限系统；
- 局域网开放和公网部署；
- 引入大型 Web/任务框架；
- 自动生成私人知识库评测题；
- 默认开启 LLM judge；
- 替换现有向量数据库；
- 重写现有 Web UI 设计系统。

## 5. 发布门槛

只有同时满足以下条件，才认为 P0/P1 完成：

1. 标准测试入口可发现并执行全部离线测试；
2. 记忆、联网、密钥和任务写回均有可验证的用户控制或安全边界；
3. 任务不会永久卡死、重复写回或跨会话串线；
4. 评测报告包含失败样例、分位数和题型分层结果；
5. 旧 `Agent.ask()`、`/api/ask`、`/api/ask_stream` 行为保持兼容；
6. 新增 API 和配置均有文档与错误契约。

## 6. 首个迭代建议

第一迭代只做 P0-1、P0-2、P0-3：

- 先让质量信号可信；
- 再让用户能控制记忆；
- 最后收紧默认数据外发和持久化行为。

这三个完成后再进入 P1 解耦和任务并发，否则会在不稳定的基础上继续扩展复杂度。
